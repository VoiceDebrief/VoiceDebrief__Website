# Bug Report (upstream): A Mislabelled `.ogg` Produces A HALLUCINATED Transcript, Silently

**From:** whatsapp-transcribe team (this repo) — Dev + QA
**To:** `SGraph-AI__Tools` — audio-transcribe maintainers
**Date:** 5 August 2026
**Severity:** HIGH — silent data-integrity failure, not an error. Affects the live
`tools.sgraph.ai/en-gb/audio-transcribe/` tool and every embedder of the engine.
**Reproduced:** 5 Aug 2026, real OpenRouter key, real WhatsApp voice note, 4/4 runs.

---

## Summary

A WhatsApp voice note whose file the OS labels `application/ogg` or `video/ogg` (both
common `.ogg` registry mappings on Windows and Linux) is passed to the model **without
decoding and with that non-audio MIME in the data URL**. The model cannot decode it,
**does not error**, and returns a confident, fluent transcript of audio the user never
recorded. Same bytes labelled `audio/ogg` transcribe correctly.

## Evidence

One file (`OggS` + `OpusHead`, 14 KB, real voice note saying *"This is me recording a
voice memo that we can use in our tests."*), varied only by the `File.type`:

| `File.type` | Transcript returned |
|---|---|
| `audio/ogg` (control) | ✅ "This is me recording a voice memo that we can use in our tests." (every run) |
| `application/ogg` | ❌ "There was a sound of footsteps in the corridor." |
| `application/ogg` (rerun) | ❌ "The government has spent up to 13 million pounds since 2004 on paying…" |
| `video/ogg` | ❌ "The current system is not capable of handling these requests." |
| `video/ogg` (rerun) | ❌ "The government has approved a change in planning rules to make it easi…" |

Different fabrication each run — the model is hallucinating over undecodable input.

## Root cause (in source)

1. `core/sg-audio-decode/…/sg-audio-decode.js` → `needsDecode()`:
   `if (ext && OR_SUPPORTED.includes(ext)) return false` — `.ogg` short-circuits on the
   **extension** before the MIME is considered, so no decode happens.
2. `en-gb/audio-transcribe/api/audio-format.js` → `toSupportedDataUrl()` then builds the
   data URL from `blob.type`, i.e. `data:application/ogg;base64,…` — a non-audio MIME
   declaring audio payload.
3. The provider accepts the request and the model invents text.

Note the same file already carries a prescient comment for `.opus`: *"per-model `ogg`
acceptance is unverified; we decode it to WAV"*. That caution is right — it just isn't
applied to `.ogg`, which is the **same Opus-in-Ogg bytes** under a different name.

## Suggested fix (upstream)

1. **Never trust a non-audio MIME.** In `needsDecode()`, if the MIME is present and does
   not start with `audio/`, return `true` (decode) regardless of extension.
2. **Prefer content over extension.** Sniff the leading bytes: `OggS` + `OpusHead` →
   Opus-in-Ogg → always decode (as `.opus` already does). Our implementation of this is
   [`website/app/audio-normalise.js`](../../../../website/app/audio-normalise.js) —
   ~60 lines, MIT-compatible, take it wholesale if useful.
3. **Fail loudly, never silently.** If a request returns text but the audio was passed
   through in a format that could not be verified, that is worth surfacing — a wrong
   transcript is far more damaging than an error message.

## What we did meanwhile

This repo normalises by content before calling `addFiles`, so our users are unaffected
from v0.1.15. We did **not** fork the engine — the fix sits in our layer and the engine
keeps its never-fail decode path. Issue: [`issues/done/025`](../../../../issues/done/025-ogg-mime-hallucinated-transcript.md).
