# Review: the TTS JS API diagnostic — the agent was right

**Reviewed** 12 August 2026 · **Source** an external agent's
`VoiceDebrief_TTS_JS_API_Diagnostic.md`, run against
<https://qa.voicedebrief.ai/tools/text-to-speech/> (build `v0.1.26-qa.5a9ce5a`)
· **Issue** 064

## The report

Method: a real Chromium session, navigate → wait for `readyState === "complete"`
→ `typeof window.__tool` → recheck ~1.5s later. Result both times: `undefined`.
It stopped short of a diagnosis, listed five hypotheses, labelled them
"hypotheses, not observed facts", and deliberately did not press the button or
enter a key because that would spend money. That is a good report.

Its five hypotheses included the right one (#3, "registration timing or
lifecycle") and its recommended next step — read `tts-page.js` and find where
`window.__tool` should be assigned — was the correct one.

## What was actually wrong (measured, not assumed)

Reproduced by serving the **deployed bytes** to a real browser and routing the
engine origin two ways:

| condition | `__tool` at `readyState=complete` | after the agent's +1.5s | ever |
|---|---|---|---|
| engine origin reachable | `undefined` | `object` | **1860 ms** after `goto` |
| engine origin blocked | `undefined` | `undefined` | **never** |

Both are failures of the same design decision: `publishApi()` was `async` and
**awaited `sg-tool-api.js` from `dev.tools.sgraph.ai` before publishing
anything**. So the advertised entry point inherited a second origin and a chain
of three sequential cross-origin module fetches.

1. **It was a race even on the happy path.** 1860 ms is *after* `readyState`
   reaches `complete`. Every natural way to check — load the page, then look —
   loses, and loses non-deterministically, which is the worst kind.
2. **It was fatal on a blocked origin.** A sandboxed browser permitted to reach
   only the page it navigated to is a normal, not exotic, agent environment. The
   report's session looks like exactly that.
3. **The dependency was not even needed.** Four of the seven actions
   (`getVoices`, `setApiKey`, `hasApiKey`, `newsScriptFor`) touch nothing on that
   origin; the other three need the *TTS* module, which is a different file
   imported at first use. The API was strictly less available than the button
   beside it, for no capability gained.
4. **The failure was invisible.** `publishApi().catch(err => console.warn(…))`.
   An agent reading console *errors* sees nothing — which is why the report's
   only console finding was an unrelated browser-extension message, and why it
   could not distinguish "still loading" from "broken". A caught error that only
   reaches `console.warn` is, for an automated caller, a silent failure.

## The fix

- **Publish synchronously.** A local implementation of all seven actions is
  assigned to `window.__tool` during module evaluation — no network, no lazy
  init, no first-click requirement.
- **Upgrade in place.** `SgToolApi` still loads and takes over the same name via
  its own registry, from **one** `ACTIONS` list shared by both, so there is no
  second definition to drift. Same `speak()` underneath; a held reference keeps
  working across the swap.
- **Never silent.** `window.__toolStatus` always exists:
  `{ ready, mode: 'local' | 'sg-tool-api', methods, engine: { origin, loaded, error } }`.
  The page also states it in a visible line.
- **Say the timing out loud** in the page, `SKILL__api.md` and `manifest.json`,
  including that `readyState` is the wrong thing to wait on.

Two browser tests lock the ordering, asserting `window.__tool` exists on the line
after `publishApi()` returns and that every action works with the engine origin
unreachable — which is the CI runner's actual condition, so the regression cannot
come back quietly.

## The lesson worth keeping

**An agent-facing API must be at least as available as the UI beside it.** If a
human can use the page, `window.__tool` must work — a remote dependency may
upgrade the API's provenance but must never gate its existence. And an
automated caller cannot see a `console.warn`: readiness and failure both have to
be *state*, queryable at any time, not events you had to be listening for.

The next tool in `/tools/` inherits this: publish locally first, upgrade if you
can, and always leave a status object behind.
