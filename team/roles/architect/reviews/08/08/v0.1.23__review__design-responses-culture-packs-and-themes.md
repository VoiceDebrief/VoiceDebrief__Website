## Grounding: verified, not assumed

Before judging the design, I checked whether the packs were built against the
real app or an imagined one. They are real: the shared `tool-adapter.js` uses
the app's actual key name (`sg-openrouter-mgmt-key`, matching `engine.js` and
`wa-key-panel`), the actual event vocabulary (`wa:ingested`, `wa:transcript`,
`wa:summary`, `wa:pass:complete` — all in `manifest.json`), and the actual
`runPass` contract from `SKILL__api.md`. Fixture mode and live mode share one
code path, which means the prototypes are demoable with no key and truthful
with one. This is the difference between a design hand-off and a mood board.

## The culture pack: the stronger of the two

Four cultures (en-gb, en-us, pt-pt, pt-br) as complete packs — theme tokens,
`core.json` strings, `culture.json` data — in one switchable prototype.

**The best idea is the one nobody asked for: the explanation layer.** Numbered
markers on every element that differs, each giving what changed / why / an
evidence line citing the decision it derives from, plus a ten-row compare
matrix with a "why it matters" column. The notes differ per locale — en-gb's
marker argues British product vocabulary, pt-pt's argues `ficheiro` vs
`arquivo`, pt-br's argues why "Resumão" has no pt-PT equivalent. This is the
standing answer to "why four packs instead of two languages", it is the
material behind Dinis's culture-MVP LinkedIn post, and it should survive as a
public page eventually — it is the argument, not decoration.

**Craft that earns trust:**
- Authentic vocabulary splits (ficheiro/arquivo, dispositivo/celular,
  ecrã/tela, utilizador/usuário) — the Translator role's "different cultures,
  not different spellings" rule, honoured in the strings themselves.
- Correct per-culture number/date conventions: `1 234,5` (pt-PT, narrow-space
  thousands, symbol after) vs `1.234,5` (pt-BR), `8 August 2026` vs
  `August 8, 2026`.
- GBP declared in every pack, never hardcoded — Dinis's 8 Aug decision,
  carried through.
- No flags anywhere in the picker; native-script names — implementing the Send
  designer decision that was recorded there and never shipped.
- A real accessibility catch: pt-BR's bar is its accent colour, so every pack
  declares an explicit `barAccent`/`onBarAccent` pair — without it the
  picker's selected state vanishes. Keep that token pair.
- Culture-specific affordances beyond strings: pt-BR's circular drop target
  where pt-PT's is square — the locale folder as home for culture-specific UI,
  exactly as the strategy described.

## The themes pack: three theories of guidance, honestly instrumented

Studio (editorial calm, crumb line + "next:" lines), Console (pipeline rail
with `[ok]/[now]/[  ]` markers and a live spend meter), Card (phone-app
stepper + one sticky next-action button). Three genuinely different bets on
*how the user is told what happens next*, over the identical flow — and they
deliberately avoid the estate's navy and WhatsApp green so the A/B measures
theme rather than familiarity.

Disciplines worth naming:
- The free demo path is honestly labelled everywhere ("£0.000 — cached,
  nothing was called").
- A caught-in-review bug guard is documented and must be kept: `reset()`
  clears the demo flag, otherwise a real file after a demo skips the key
  screen and the cost line lies.
- Privacy and cost sit adjacent to the button that acts on them — "never a
  footer, never quieter than this".
- Telemetry is local-only (`localStorage`, never sent) — consistent with the
  "nothing tracked" claim while the A/B measurement question (strategy §6)
  stays open.
- The fixture streamer is time-driven with a hard deadline, with an explicit
  warning not to "improve" it to `requestAnimationFrame` (paused in hidden
  tabs). Correct, and the warning belongs in the port.

## The five integration flags (also in the responses README)

1. **Theme-per-locale vs independent axes — the one architectural tension.**
   The culture pack binds a token sheet to each locale (`themes/pt-br.css`);
   shipped M1 keeps themes and locales as independent allowlists, which the
   A/B needs (crossing arms × locales). Resolution: a locale's `culture.json`
   **names a preferred theme** from the theme allowlist. Axes stay
   independent; cultures keep their identity; the picker applies both.
2. **A recorded rule is knowingly reversed**: Send's designer review specifies
   a culturally neutral palette; the culture pack gives each culture its own
   identity in colour, type and shape. That was the ask and it is defensible —
   recorded here as a decision so it never reads as an oversight.
3. **The themes drop the site nav** — deliberate for A/B arms, but a decision:
   they belong under `/design/`, noindexed, out of the sitemap; llms.txt only
   if they graduate to public surfaces.
4. **Upstream request worth acting on**: all three themes are built around
   watching words arrive, and no partial-transcript event exists today. The
   pack calls a transcript stream "the single highest-value engine change" —
   that is a `team/comms/briefs/` request to the Tools team.
5. **en-us arrives as a bonus fourth culture** beyond the pt pair M2 named —
   welcome, gated draft like any other locale.

## Timing

The M2 skeleton (four locale folders + `wa-locale-picker`) landed on `qa`
while this review was being written — the pack's tokens, strings and culture
data now have exact slots waiting. Settle flag 1 first; everything else is
drop-in. Not designed anywhere yet, and known: error states per theme,
chat/flow/debug/errors domains for any locale, RTL (logical properties from
day one), draft-locale presentation in the picker.
