## The Allowlist (verified in code, v0.1.20)

Five models. Every model id the app can send to OpenRouter, with where it is pinned:

| Model | Used for | Pinned in |
|-------|----------|-----------|
| `google/gemini-3.5-flash` | Transcription-path default, summary (`ask`), chat default, drawn-SVG infographic | `engine.js:16`, `chat.js:18`, `infographic.js:22` |
| `google/gemini-3.1-flash-image-preview` | Infographic **default** (finished image) | `infographic.js:20` |
| `google/gemini-2.5-flash-image` | Infographic alternative (finished image) | `infographic.js:21` |
| `anthropic/claude-sonnet-4.5` | Chat option ("deeper answers") | `chat.js:19` |
| `openai/gpt-5-mini` | Chat option | `chat.js:20` |

**One caveat to verify at configuration time**: the transcription call goes through
the imported engine, whose active model comes from the upstream `audio-models.js`
list (`state.getActiveModel()`, `engine.js:71`) — seven chat-path models upstream.
If the engine's default differs from `google/gemini-3.5-flash`, the debug pane's
exchange log will show the actual id on the first transcription; add it to the
allowlist or pin the engine's model explicitly. **This is also the enforcement
working as designed**: with the guardrail in place, any model outside the allowlist
is rejected server-side, whatever the client asks for.

## Recommended Key Configuration (apply on OpenRouter)

For every key this product issues or seeds — starting with any beta key:

1. **Model allowlist**: exactly the five ids above. This converts a found key from a
   general-purpose credential into a bounded one (brief v0.33.53, key claim 5).
2. **Hard spend cap** per key, with a reset period — cap value to be fixed in the
   seeded-key conditions doc (below); for BYOK-era test keys, small (e.g. $5).
3. **Provider / data-policy restriction**: not needed for the routed (default) tier;
   it is the lever that makes the **restricted** privacy tier enforceable
   server-side (issue 014). Configure when that tier ships — but while in the
   dashboard, record which of these controls the *personal* account actually
   exposes, since OpenRouter documents some guardrail administration as
   organisation-account features. That observation is the missing input to issue
   014's automation question (management API vs dashboard-only).

Client-side, no change is needed for D2: the UI's model pickers already offer
exactly the allowlist (`CHAT_MODELS`, `INFOGRAPHIC_MODELS`), and the chat tool
registry validates model ids against them.

## What This Doc Deliberately Does Not Cover

The **seeded-key conditions** (cap value, lifetime, revocation trigger and drill,
the transition point at which a seeded key stops being acceptable) — required
*before* any key ships, per issue 010 and AppSec's ROLE. That is the next AppSec
document, unblocked today by D1/D2; the allowlist above is its first ingredient.
