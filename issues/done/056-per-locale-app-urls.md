# 056 — One real URL per language: /app/pt-pt/, /app/en-us/ …

**State:** done · **Priority:** high · **Effort:** medium
**Opened:** 2026-08-08 · **Closed:** 2026-08-08 · **Requested by:** Dinis

## Why

A language you can only reach by clicking a picker cannot be linked to, shared,
bookmarked, or indexed. Dinis: *"we need to support directly linking to the
translated page"*.

## Real files, not client-side routing

`/app/pt-pt/` is a directory with an `index.html`, generated by
`scripts/build_locale_pages.py` from the locale allowlist. GitHub Pages cannot
rewrite `/app/pt-pt/` to `/app/`, so a path that only works because JavaScript
rescues it is not a shareable link — it is a 404 with good intentions. The URL
works before a line of our code runs.

Each generated page differs from the source in four ways:
`<base href="../">` so every relative reference still resolves to `/app/`;
`lang` in proper BCP-47 casing (`pt-PT`, not `pt-pt`); a self-canonical, because
these are distinct pages and pointing them all at `/app/` would ask search
engines to drop them; and the full `hreflang` set plus `x-default` → `/app/`.

## The security question, answered before it was asked

A path segment that decides what the page loads is the same *shape* as the
`?origin=` problem (issue 041). The difference is total and worth stating: that
value was used to build an import URL, so any string became executable. Here the
segment is turned into an **allowlist key** — an unknown or hostile segment fails
the lookup and falls through to detection, and the locale files are fetched from
the key, never from the path. `/app/../../evil/` is a non-key like any typo.

## Precedence: the URL wins

Path → stored choice → `navigator.languages` (live locales only) → default.
The URL has to beat a stored preference, or shared links would work for everyone
*except* the people most likely to be sent them. Opening a locale's URL is itself
an explicit choice, which is why it may serve a draft locale that would never be
auto-assigned.

Switching in the page rewrites the address bar with `replaceState` rather than
reloading: a reload would discard an in-flight pass and the chat thread, and a
URL still saying `/app/pt-pt/` over an English page is a link that lies when
shared. The target pages really exist, so refresh and copy-paste both work.

## A bug the tests caught

`replaceState` moves the document URL, and **relative fetches resolve against
it**. On the bare `/app/` page — which had no `<base>` — switching language made
`./workflows/standard.json`, `./locales/`, `./prompts/` all resolve one level too
deep, from that moment on, silently, and only for users who changed language.
The source page now pins `<base href="./">` and the generator rewrites it to
`../`; both are immune. Gated in `app-boot.test.mjs`: the URL moves AND a
relative fetch still resolves afterwards.

## Gates

- `build_locale_pages.py --check` in both pipelines, and it checks BOTH ways:
  the source page's `hreflang` set must match the allowlist exactly. Adding a
  locale without its URL, or advertising a URL for a locale that does not exist,
  fails the build. Negative-tested.
- Live-QA fetches all four locale URLs and asserts each page's own `lang` — so
  a generator that wrote four copies of the same page is caught, not just a
  missing file.
- `app-boot.test.mjs`: URL rewriting, relative-fetch survival, return to `/app/`.

## Not done

The content estate (`/pt-pt/updates/` etc.) and `sitemap.xml` entries for the
locale URLs. This issue covers the app only, which is where direct links matter
most; the rest is strategy item M4.
