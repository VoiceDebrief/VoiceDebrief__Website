M1-a spike: the import harness

Does the audio-transcribe entry module run without the tool's shell DOM (Attempt 1), or must we register the method-group builders on our own SgToolApi (Attempt 2)?

What this page decides

Dev brief §2 lists three cuts, tried in order: Attempt 1 imports audio-transcribe-api.js and waits for tool:ready — free, but it calls mountShell, so it only survives if a missing shell DOM is non-fatal. Attempt 2 imports the method-group builders plus ui/state.js and registers them on our own SgToolApi — engine only, no UI expectations. Attempt 3 (iframe + postMessage bridge) is the last resort and is not automated here.

Each attempt runs inside its own throwaway same-origin iframe, so the ES-module registry and window.__tool are fresh per run and the two attempts cannot contaminate each other. Nothing here needs an OpenRouter key: the spike stops at the handshake, before any inference.

Cross-origin import() needs CORS headers on the engine origin. A blocked import fails the attempt with a network/CORS error rather than a contract error — read the raw error before concluding anything about the cut.
