# 01 — The product, and the constraints that are not negotiable

**version** v0.1.23 · **date** 8 August 2026

---

## What VoiceDebrief is

Someone exports a voice message from WhatsApp — a 30-second to 3-minute recording,
usually one person talking to one other person or to a small group — drops it on a web
page, and gets back a transcript, a translation into their own language, a short
written debrief, and optionally an infographic. It runs live at
`whatsapp-voice-transcription.sgraph.ai/app/` and on a QA estate.

**Renamed to VoiceDebrief** (Dinis, 8 Aug; `VoiceDebrief.ai` registered). The WhatsApp
version is one variant; the plural is deliberate. The code has not been renamed yet.

## What one pass produces

A declared workflow of six steps (`data/standard-workflow.json`):

```
normalise → ingest → transcribe → [translate] → summary → [infographic]
   local     engine    $0.05        $0.03        $0.02      $0.20
   abort     abort     abort       degrade      degrade    degrade
```

Two steps are optional and conditional on user choices. The `translate` step is **on
by default** and sits between transcribe and summary deliberately: **the summary and
the infographic are built from the translation when there is one**, so the debrief is
in the reader's language even when the recording is not.

Three materials come out, and each is its own artefact shown on its own card:

- **transcript** — what was said, in the language it was said. Never overwritten. It is
  the record.
- **translation** — the transcript in the reader's language. Its own material, not a
  replacement.
- **summary** — the debrief. **Its shape is fixed by the prompt** — see below.

## The summary's shape is the graph's input

This matters more than anything else in this document. `data/summary-prompt.md`
produces exactly three sections, every time:

```markdown
## Key points
3-6 bullet points capturing what the speaker actually said - concrete facts, decisions,
numbers and names, not paraphrased vagueness.

## Actions
Any tasks, follow-ups or requests mentioned, each as "- [who] what". If none, write "- none mentioned".

## In one sentence
One plain sentence a busy person could read instead of listening to the note.
```

So a semantic graph over "the summary" is a graph over **key points, actions with an
actor, and a one-line gist**. That is a much more structured input than free prose, and
a simulation should exploit it. Note in particular that `## Actions` already carries an
**actor** — which is a relation the concept model does not currently express.

Whether the graph should be built from the **transcript** (richer, messier, more
tokens, everything the speaker said) or the **summary** (structured, short, cheap, but
already lossy — the summariser has thrown away what it judged unimportant) is an open
question this simulation should help answer. Show both if you can.

## The constraints

These are architectural decisions, not preferences. A design that violates one is not
buildable here.

### 1. There is no backend

Everything runs in the front end. Hosting is static (GitHub Pages, Netlify for QA). The
only server-side code ever planned is one key-provisioning Lambda, currently deferred.

Consequences for graph work:
- **No vector store, no database, no server-side index.**
- Anything persisted lives in `localStorage` today, in a customer-held encrypted vault
  later. Neither exists as a graph store yet.
- Retrieval over a concept scheme has to happen **in the browser**, over data the page
  already has.

### 2. Inference is chat completions through OpenRouter, on the user's own key

The user brings their own OpenRouter key; it is stored in their browser and never sent
anywhere but OpenRouter. Every call costs *them* money, which is why the pass quotes a
maximum before it runs.

- We have **never called an embeddings endpoint**, and whether OpenRouter exposes one
  usefully is unverified. **Do not assume embedding retrieval is available.** If your
  design needs semantic retrieval, either justify a lexical alternative or flag the
  dependency explicitly.
- The infographic step is the only non-text call (image generation).

### 3. The whole pass is budgeted at $0.30

Each step declares a budget; the ceiling is quoted on screen before the user commits.
An ontology step must declare a budget too, and it must be quotable **before** it runs —
which means its cost cannot depend on the size of the customer's ontology in a way that
can't be predicted.

**A design costing 100 model calls per recording is not a design.** See document 05.

### 4. A strict Content Security Policy

The app page pins `script-src` to itself, two named engine origins and one CDN. No
arbitrary code loading, no eval of fetched content. Any client-side library would have
to be vendored into the repo, and heavy WASM is a real cost on a phone.

### 5. Anything that selects what the page loads must be an allowlist key

Learned the hard way (a removed `?origin=` parameter that let any URL decide which
JavaScript ran beside the user's API key). Themes, locales and — when it exists — the
workflow variant are all chosen by **naming a key in a committed index file**, never by
supplying a URL. A customer-supplied ontology is *data*, not a selector, but where it
comes from will need the same care.

### 6. Never commit secrets, and the ciphertext rule

An encrypted vault may live in the public repo; the key that opens it may not. Relevant
here because of a point document 05 makes: **an ontology distilled from fifty of
someone's private voice notes is more sensitive than any single transcript**, not less.

### 7. Front end is static HTML, vanilla JS and Web Components

No SPA frameworks. Assets are immutable and versioned (`v0/v0.1/v0.1.3/`). Components
use Shadow DOM and are styled entirely from CSS custom properties, so the whole design
is one swappable stylesheet.

## Privacy modes, because they constrain what may be sent

Three declared modes, of which only the first works today:

| Mode | Meaning |
|---|---|
| **routed** (default) | Any of our model providers may process the recording; we cannot promise which |
| **restricted** | Only approved providers — not built |
| **on-device** | Nothing leaves the device — not built |

A graph feature sends *more* content to a model, not less. Whatever is designed has to
be describable honestly in those terms.
