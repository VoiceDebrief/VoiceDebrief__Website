## Why this is a good idea for *this* product specifically

A tool that turns voice notes into writing, publishing its own news as voice
notes, is the product demonstrating its own thesis in reverse. The Updates feed
becomes listenable; the RSS becomes a podcast; and every post gains an
accessibility route it does not have today. It is also cheap: a 150-word read is
a fraction of a penny.

## What I verified before writing this (the doc is right; two details are not)

The capabilities doc is accurate about the API. Two things it says would fail if
followed literally, both checked in this container today:

1. **The module is not at `tools.sgraph.ai`.** That URL returns
   `403 AccessDenied` (S3). It *is* served, 200 and CORS `*`, from
   **`dev.tools.sgraph.ai`** — which is the origin `website/app/config.js`
   already pins. Use that, and pin the version path as everything else here does.
2. **Node cannot `import` from an https URL.** The doc's Node example
   (`import … from 'https://…/sg-tts-openrouter.js'`) fails with
   `ERR_UNSUPPORTED_ESM_URL_SCHEME` on Node 22 — network imports are behind a
   removed/experimental flag. A headless generator must **vendor** the module or
   eval it from a `data:` URL.

Also: **`ffmpeg` is not present in this environment**, so a WAV→MP3/Opus step
cannot be assumed to exist locally (GitHub runners do carry it). The API surface
itself is confirmed: `synthesizeOpenRouter(text, {apiKey, voice, model, fetchImpl})`
→ `{blob, durationMs, generationId, transcript}`, streaming `pcm16` at 24 kHz,
typed errors `no-key` / `no-fetch` / `tts-http` / `tts-no-stream` / `tts-no-audio`,
and `pcm16ToWav` / `encodeWav` exported for glue.

## The shape I propose

### 1. The script is written, not derived

The news style comes from the script, not from a mode — the doc says so, and it
is the whole difference between a broadcast and a robot reading a changelog. So
the **Journalist writes the spoken version when they write the post**, as a
section in the same markdown file:

```markdown
---
title: Your debrief really is in your language now
date: 2026-08-11
speak: true
voice: onyx
---

…the written post…

## Spoken

Here is the latest from Voice Note Transcribe. If you asked for your debrief in
Portuguese last week and got it in English — that is fixed. The translation was
right; the instruction underneath it still said "British English"…
```

Why this way, and not "read the post" or "have an LLM write the script":

- The written post has bullet lists, bold, code and links. Read verbatim it
  sounds like a form being completed. A spoken script is a different register.
- **It stays reviewable in the diff.** Everything else the Journalist publishes
  is reviewed as text before it ships; the words a synthetic voice says in our
  name deserve the same. An LLM-written script would be a second billed call
  producing unreviewed copy — and the same person is already writing the post.
- **Absent script → no audio, visibly.** A post without `## Spoken` simply has
  no audio, which is honest and gradual: the back catalogue fills in when
  someone wants it, and nothing ships a bad read to look complete.

### 2. Generation is a deliberate act, not a deploy step

`scripts/build_audio.mjs`, run by hand or by `workflow_dispatch` — **not** on
every push. Three reasons: it spends money (every deploy would re-spend or need
careful skip logic); deploys must stay repeatable and secret-free; and the output
is a committed artefact, like the screenshot baselines.

- Key from `OPENROUTER_KEY` in the environment. Never committed, never a default.
- **A declared ceiling**, in the spirit of the workflow's per-step budgets:
  `--max-usd 0.25` refuses to start work that would exceed it, and reports what
  it spent. A generator that can silently spend is a generator nobody will run
  twice.
- **Hash-skip**: a manifest records `sha256(script + voice + model)` per post.
  Unchanged script → no call, no spend, no churn. Same discipline as
  `baseline-changes` — record what moved, and why.

### 3. Vendor the TTS module, with provenance

Given constraint (2) above, and this estate's instinct that **nothing remote
decides what runs** (issue 041), the generator should import a **vendored copy**
at `scripts/vendor/sg-tts-openrouter/v0.1.0/`, with a README naming the source
URL, the version and the retrieval date — exactly as QUnit is vendored for the
browser tests. The alternative (fetch + `data:` URL eval at build time) pulls
executable code from the network into a process holding an API key, which is
precisely the shape this repo removed on purpose.

### 4. Format, size and the feed

- The API returns **WAV** (24 kHz mono 16-bit) ≈ **2.9 MB per minute** — too big
  to commit per post.
- **MP3 64 kbps mono ≈ 0.5 MB/min** (universal in podcast clients);
  **Opus ~24 kbps ≈ 0.18 MB/min** (smaller, and pleasingly the product's own
  format, but weaker client support).
- Proposal: **MP3 for the enclosure**, encoded with `ffmpeg` where present, and
  the generator **fails loudly** if it is missing rather than committing WAV.
  A 150-word read is ~1 minute, so a year of daily updates is ~180 MB — which
  argues for keeping only recent audio in git, or moving to object storage if
  this becomes daily-for-ever. **Flagged as the one thing that does not scale
  quietly.**
- Publishing: `updates.json` gains `audio: {url, durationMs, bytes, voice, model, sha}`;
  `feed.xml` gains `<enclosure>` (the RSS becomes a podcast feed); the Updates
  page gains an `<audio controls>` per post; `llms.txt` lists the manifest, in
  the same commit, per the rule.

### 5. It must say it is synthetic

A site whose product is voice, publishing a synthetic voice, must label it.
Every player and the feed description carry it: **"Read by a synthetic voice
from a script written by the team's Journalist."** Not a disclaimer in a footer.

### 6. How it gets tested without spending anything

`synthesizeOpenRouter` accepts **`fetchImpl`** — so the whole generator can be
driven against a scripted fetch that returns a tiny PCM stream, exactly as the
chat-loop suite scripts OpenRouter today. That gives a deterministic unit test
for chunking, the hash-skip, the manifest, the ceiling and the WAV wrapping,
with no key, no network and no cost. The one thing it cannot prove is that the
voice sounds right — which is a listening decision, not a test.

## Milestones

- **A1 — one post, by hand.** Vendor the module, write `build_audio.mjs`,
  generate one real MP3 from one `## Spoken` section, listen to it. This is the
  cheapest possible answer to "does this sound like something we want?"
- **A2 — the pipeline.** Manifest + hash-skip + ceiling + the scripted-fetch
  test; `updates.json`, the page player and the RSS enclosure; the synthetic-voice
  label; live-QA fetches one audio file so a broken path cannot ship quietly.
- **A3 — routine.** The Journalist writes `## Spoken` with every post; a
  `workflow_dispatch` job for whoever holds the key.
- **A4 (later, tied to issue 050) — the other cultures.** pt-PT and pt-BR reads.
  The OpenAI voices are English-first; quality in Portuguese needs listening to
  before it is promised. The scripts are already per-locale data by then.

## Decisions I need from Dinis

1. **Voice**: `onyx` (deep, anchor-like) or `echo`? One voice, kept consistent —
   it becomes the sound of the product.
2. **Where it runs**: your machine / the Journalist agent's session (key stays
   local, audio committed) — or a CI secret and a dispatch button? I lean local
   first, CI once the shape is proven.
3. **How much back catalogue**: only new posts from now, or fill in the recent
   ones? (23 posts exist; ~£0.20 and an hour of listening to check them.)
4. **Storage**: commit the MP3s (simple, self-contained, grows) or park them in
   S3/CloudFront (cheap, unlimited, one more moving part)? Committing is right
   for now; the answer changes if this becomes daily for a year.
