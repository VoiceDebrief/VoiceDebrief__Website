## The Pattern (as briefed)

A dedicated **"QA to docs"** test set with two functions at once:

1. **Final QA of the key user features and workflows** — validating that the latest
   changes broke nothing a user actually does; and
2. **Screenshot capture that creates and maintains the user-facing docs** — the same
   run that proves a feature works produces the images that document it.

Executed with Playwright inside the CI pipeline (GitHub Actions here). The load-bearing
addition is an **image-diff calculation** over the screenshots: comparing each new
capture against its committed baseline so the pipeline can tell *pixel noise* (a few
pixels of rendering drift) from *actual UI/UX change* — the former is ignored, the
latter is either a caught regression or an intended change whose documentation
updates itself in the same motion.

One run, three outputs: a pass/fail QA verdict, always-current user docs, and a
visual change log of the product's UI over time.

## Why This Repo Is Unusually Ready For It

- **The hard part already exists.** The `chat-loop` integration test scripts a mock
  OpenRouter through a *deterministic, keyless full pass* — drop → transcript →
  summary → infographic → chat tool call. Deterministic LLM output is exactly what
  screenshot stability requires, and this repo already has it.
- **CI already commits back to the repo** (the version bump), so a job that commits
  refreshed baselines is in-pattern, not a new trust decision.
- **The site is static**, so docs pages embed committed images directly — no asset
  pipeline.
- **It closes review findings directly**: no user guide or FAQ exists (doc 05 §3);
  the default image-infographic path has zero test coverage (doc 03 §2.1); and the
  record-staleness class (doc 01, tension 1) cannot afflict docs whose images are
  regenerated on every deploy. Screenshots produced by CI are the visual counterpart
  of the reality doc: **docs that can't lie**.

## Proposed Design

### The journeys

`tests/qa-to-docs/` — one script per user journey, each a sequence of QA assertions
*and* named captures at the story moments:

| Journey | QA proves | Captures for the docs |
|---------|-----------|----------------------|
| First visit + key setup | key panel save/validate flow | landing, key panel, "key saved" state |
| The one pass (sample note, mocked LLM) | drop → transcript → summary → infographic all arrive, in order, with progress | drop zone, progress rail mid-pass, each result card |
| Infographic v2 | model picker, redraw, save | picker open, redraw heartbeat, finished image card |
| Chat with the materials | context rows, a tool call, edit + restore | chat panel, tool call in thread, "✎ edited… restore" note |
| Debug pane | exchange log, prompt templates | pane open on each tab |
| The record | versions page renders, chip present | versions timeline |

A `journeys.json` manifest names every shot: id, journey, caption, which user-guide
page slot it fills, and its **mask list** (see below).

### Determinism (what makes the diff meaningful)

Fixed viewport and device scale; animations disabled; the mock OpenRouter transport
supplying identical LLM output every run; and per-shot masks over the legitimately
dynamic regions — version chip, cost figures, elapsed-time tickers — declared in the
manifest, not hardcoded. One rule keeps rendering consistent forever: **baselines are
only ever produced in CI** (pinned runner image + bundled fonts), never on a laptop.

### The diff gate

Baselines live in the repo (e.g. `website/user-guide/screenshots/`, served as site
assets). Each CI run recaptures and compares per shot (pixelmatch/odiff, per-shot
threshold, antialiasing tolerance):

- **Below threshold** → pixel noise: keep the committed baseline, no churn commit.
- **At/above threshold** → real UI change, two honest cases:
  - *Unintended* → a **caught visual regression**; the job fails with a side-by-side
    + diff-overlay report as the artifact. This is QA function (a).
  - *Intended* → the change is acknowledged by refreshing the baseline in the same
    branch/commit as the feature (or a CI auto-commit alongside the version bump,
    once trusted) — and the user docs are thereby already updated. This is
    function (b). The acknowledgement itself becomes a changelog-able fact: "the UI
    changed here, on purpose".

### The user guide it feeds

`website/user-guide/` — static pages whose prose is stable ("Paste your OpenRouter
key…") and whose images are manifest-referenced screenshots. The guide doubles as
FAQ raw material (doc 05 §3.3) and — per doc 06 — `/engineering/testing/` surfaces
the journeys, their last verdicts and the latest visual diffs: the "screenshots that
can't lie" story is prime material for the entrepreneur series (*instalment: your
docs should be a build artefact*).

### CI wiring

Runs in the existing test job against the local server (same harness as the
integration tests), gating the tag like everything else; on the `qa` branch it can
additionally recapture from the deployed Netlify build. Diff reports upload as
workflow artifacts on failure; the manifest + latest results feed `status.json`
(doc 06) so the hub shows them.

## Sequencing

1. **M-qtd-1** — harness + diff gate + two journeys (the one pass; chat), baselines
   committed, reports on failure. One focused session, mostly recomposing the
   existing chat-loop machinery.
2. **M-qtd-2** — full journey set + the `website/user-guide/` pages that embed them.
3. **M-qtd-3** — intended-change auto-refresh flow + hub surfacing (with issue 036).

## Open Questions

| Question | Note |
|----------|------|
| Baseline refresh policy | Manual-in-branch first (reviewable), CI auto-commit later once the threshold tuning has earned trust |
| Threshold per shot or global | Start global (e.g. 0.1% of pixels after masks), override per shot in the manifest where needed |
| History | Keep only current baselines in git (diffs live in run artifacts); revisit if a visual timeline becomes hub content worth the repo weight |
| Mobile viewports | The audience is phone-first (doc 05) — a second viewport per journey doubles capture cost but may be the more honest docs; decide at M-qtd-2 |
