## What Nine Days Produced

The repo was bootstrapped on 28 July. As of 6 August (v0.1.20, 35 issues, 27 done):

- **The product is live and real.** The full one-pass — drop → transcript → summary →
  finished-image infographic — verified end-to-end with a real key on 5 August
  (5.3s / 14.7s / 53s, £0.003 per pass). On top of the milestone: a debug pane with a
  full LLM exchange log and editable prompts, sample notes, GBP cost display, and the
  M3 chat that talks to the materials, drives the tool through a typed 13-tool
  registry, and can even edit the transcript with a restore path.
- **The pipeline is grown-up.** CI gates tag-and-publish on 22 unit tests plus an
  11-check Playwright integration boot; a post-deploy job runs 16 live checks against
  the CDN; a second estate (`qa` → Netlify) deploys stamped pre-release builds. Cache
  busting exists because a real bug (issue 026) demanded it.
- **The knowledge system mostly works.** Reality doc, issues-fs-lite queue, changelog +
  updates + versions triad, dev packs, code-verified capability guides for both
  upstream tools, and real incident write-ups (the `.ogg` hallucination fix in issue
  025 is a model of the genre, complete with regression tests and upstream bug
  reports).
- **The working method is proven.** Brief → build → debrief survived a hand-off: Jose
  and two other agent sessions contributed while the original session was away, and
  the discipline held well enough that a returning agent could reconstruct everything
  from the record. That is the actual test of a documentation system, and it passed.

For context: most vibe-coded products at day nine have none of this. That contrast is
itself an asset — see doc 06.

## Four Tensions That Need Attention

**1. The public record slipped exactly when velocity peaked.** The changelog's
"rename Unreleased on tag" rule hasn't been followed since v0.1.11; `versions.json`
stops at v0.1.18 while the site serves v0.1.20; the newest Updates post links to a
404 (issue 034 moved to done); the reality doc contradicts itself about whether the M3
chat is live; two dev packs still say PROPOSED about shipped work. Individually
trivial — collectively they erode the one promise this project stakes its story on:
*the record is true*. (Details: docs 04 and 05.)

**2. The open queue is the commercial/security layer, and it is stalled on two
28-July decisions.** Everything still open (009, 010, 013, 014, 015) traces back to
brief v0.33.53's settle-first table: personal-vs-organisation OpenRouter account, and
the model allowlist. Every open issue's status note is frozen at 28 July. Meanwhile
the product went live BYOK-only — so the seeded-key cohort, the thing the commercial
model needs next, is blocked on decisions that take an afternoon. (Details: doc 04 §3.)

**3. Security posture lags the product's liveness.** The sharpest finding of the
whole review: `?origin=` on the live app page will dynamically import and execute
JavaScript from any attacker-supplied origin — in the same origin where the user's
OpenRouter key sits in plaintext localStorage, with no CSP to intervene. A crafted
link is enough. Behind it: the chat's `set_prompt` tool lets model output persist
prompt overrides across sessions (a prompt-injection prize), the ciphertext rule still
has no pre-commit enforcement (issue 013), the AppSec seeded-key conditions doc that
issue 010 requires "before any key ships" doesn't exist, and neither does the privacy
notice the DPO role and the live site both promise. None of this is exotic to fix;
all of it should precede the seeded key. (Details: doc 02 §4, doc 07 group B.)

**4. `main` is production in name only.** CI on `main` runs tests and mints a *major*
tag, but no deploy job exists for it; the production domain serves `dev` builds. The
"two branches, two estates" story in the public docs doesn't match the wiring. Either
promote the topology or amend the story. (Details: doc 03 §3.)

## The One Big Opportunity

The engineering discipline above is genuinely differentiating — and completely
invisible on the site. There is no public surface for CI status, test results, the
issue queue, or the security posture; the Library page links every reader out to
GitHub. Doc 06 proposes the **open engineering hub**: a `/engineering/` section
rendered from CI-emitted JSON (the proven `/versions/` pattern), telling the NFR story
— pipeline, testing, docs, security, team — to the GenAI entrepreneur who has
vibe-coded a service and needs to grow it up. It converts the admin estate into both
a collaboration surface and the discoverability engine the "journey is the story"
strategy is missing.

## The Shape Of The Fix

In one line each (full ordering and sizing in doc 07):

1. Fix the record first — hours of work, highest trust impact.
2. Close the `?origin=` hole and add a CSP before anything else ships.
3. Write the AppSec key conditions + privacy notice; then unstall the key/guardrails
   queue with the two human decisions.
4. Build the engineering hub on the corrected record.
5. Keep the cadence: the discipline is the product's second story — resource it like
   product work, not housekeeping.
