## The Idea (as briefed)

A public set of pages that gives a nice view of the *admin* side of this project — the
CI, the testing (unit, integration, QA), the documentation estate (architecture,
security, runbooks), the issue queue, the team — i.e. the **Non-Functional
Requirements made visible**. It serves two purposes at once:

1. **Collaboration surface.** Humans and agents joining the project get one page that
   answers "what state is everything in right now?" — instead of stitching it together
   from the reality doc, the workflows, and the issue READMEs.
2. **Marketing surface.** "The journey is the story" is a stated strategy. The
   engineering discipline here — CI auto-tagging, a three-layer test gate, a QA estate,
   a Librarian-maintained reality doc — is genuinely differentiating content, and today
   it is **invisible** on the site. The target reader is the GenAI entrepreneur who has
   vibe-coded a working service and now needs to grow it up: this hub shows them, with
   a live worked example, what "grown up" looks like and how little infrastructure it
   actually requires (no backend, no dashboard SaaS — a static site and CI-emitted JSON).

This is the same move the product itself makes: the architecture *is* the privacy
story. Here, the pipeline *is* the credibility story.

## Why This Fits This Repo Unusually Well

- The site is static and CI already stamps artefacts into it at deploy time
  (`version.txt`, cache-busters, `versions.json` is rendered client-side). Emitting a
  few more JSON files at deploy is zero new architecture — it is the established
  pattern of `/versions/` applied to more data.
- The raw material already exists and is already public: `issues/` with per-folder
  READMEs, `tests/` (22 unit + 11-check integration + 16-check live QA), two workflow
  files, the reality doc, CHANGELOG, role files. The hub is a *rendering* problem,
  not a data-collection problem.
- Issues 013/016 already point at an "admin" estate (admin vault, CRM-on-vault). The
  hub is the **public, non-secret half** of that admin story — and drawing the line
  between the two halves publicly is itself a great piece of content (the ciphertext
  rule explained).

## Proposed Shape: `/engineering/` (the "Engine Room")

One hub page plus five sections. All static, all rendered client-side from JSON that
CI emits at deploy time — exactly like `/versions/`.

```
/engineering/                     the hub: live status strip + section cards
    /engineering/pipeline/        CI/CD: the two workflows explained, last-run status,
                                  the tag→publish chain, cache-busting, QA estate
    /engineering/testing/         the test pyramid: unit / integration / live QA,
                                  counts and last results, what each layer catches
                                  (with real caught-bug stories: issues 025, 026, 029, 032)
    /engineering/docs/            the documentation system: brief→build→debrief loop,
                                  reality discipline, changelog/updates/versions triad,
                                  the Librarian + Journalist roles
    /engineering/security/        the security posture: BYOK + no-backend threat model,
                                  privacy modes, the ciphertext rule, seeded-key
                                  conditions, what is deliberately NOT collected
    /engineering/team/            the agentic team: 11 roles, how briefs/debriefs work,
                                  the issue queue rendered live (open/blocked/done)
```

### The data files CI emits (the whole backend)

| File | Written by | Contents |
|------|-----------|----------|
| `engineering/status.json` | both workflows, at deploy | tag/version, timestamp, branch, commit, per-layer test results (`unit: 22/22`, `integration: 11/11`, `live-qa: 16/16`), deploy target |
| `engineering/issues.json` | CI step (script over `issues/`) | every issue: id, title, state, priority, created, source-brief link |
| `engineering/docs.json` | CI step (script over `library/` + `team/`) | the doc inventory: path, title, type, version, date — powers a rendered library index |
| `versions.json` | already exists | unchanged — the hub links to `/versions/` |

A small `scripts/emit_engineering_json.py` (same style as `stamp_cache_busters.py`)
generates these; the workflows call it after tests, before publish. Failure states are
content too: if a layer fails on a QA run, `status.json` says so — an honest red badge
is worth more than a permanent green one.

### What each page is, editorially

Each page follows one format: **the principle** (why this NFR matters, ~3 paragraphs
addressed to the vibe-coding entrepreneur) → **the live view** (rendered JSON: current
state, real numbers) → **the receipts** (links to the actual workflow file, test files,
caught bugs, doc sources in the repo). Principle, instance, proof — that triad is the
hub's voice. Nothing aspirational goes on these pages without a `PROPOSED` label; the
reality discipline applies to marketing surfaces exactly as it does to the reality doc.

The **caught-bug stories** are the best content this repo owns and are already written
(changelog + updates): the `.ogg` MIME hallucination (issue 025 — *a test fixture and
content sniffing beat trusting the browser*), stale cached modules (026 — *why CI
stamps cache-busters*), the disabled-key "Failed to fetch" diagnosis (032 — *the debug
pane paying for itself*). Each is a one-screen story of an NFR earning its keep.

### The series for the target reader

On top of the hub, a short numbered series (published via `/updates/` and/or the
library) aimed explicitly at the GenAI entrepreneur:

*"You vibe-coded a service. Now what?"* — 1: version everything, tag from CI ·
2: three layers of tests, none optional · 3: a changelog is a product feature ·
4: docs that can't lie (reality discipline) · 5: security when you have no backend ·
6: shipping a QA estate for £0. Each instalment links to the corresponding hub page
as the living example. This is the discoverability engine (search, social, HN) that
drives visitors *to* the hub; the hub is what convinces them to stay.

## What Stays Private (the line, drawn publicly)

The hub shows state, not credentials. Explicitly out: the OpenRouter management
console/keys, the admin vault contents and its key, Netlify/AWS tokens, any customer
records (future CRM, issue 016). The `/engineering/security/` page should state this
boundary in the ciphertext-rule table form — "what MAY be public / what MUST NOT" —
because explaining the line is more convincing than hiding its existence.

## Sequencing (proposed)

1. **M-hub-1 — the record + status.json + hub page.** Fix the public record first
   (versions.json/changelog/dead links — doc 07, R1), then: CI emits `status.json`,
   `/engineering/` renders it, and `issues.json` renders the queue. Immediate value to
   agents and humans; the site gains its first live engineering surface.
2. **M-hub-2 — the five section pages**, largely editorial, drawing on existing docs.
   The security page doubles as the missing public trust page (site review, doc 05).
3. **M-hub-3 — the entrepreneur series**, one instalment per week alongside normal
   Journalist posts; each is cheap because the hub page it points to already exists.

Effort estimate: M-hub-1 is one focused session (the `/versions/` pattern is proven);
M-hub-2 is editorial work across 2–3 sessions; M-hub-3 is ongoing Journalist cadence.
