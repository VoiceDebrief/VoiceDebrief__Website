# Guide: The Tech Stack And Workflow Of This Project

*Part of the [project library](https://whatsapp-voice-transcription.sgraph.ai/library/) — every doc behind this product, organised by audience.*


**version** v0.1.0
**date** 29 July 2026
**from** Claude (session agent), reviewed against Dinis's briefs and the sibling repos
**to** Developers and partners joining the project
**type** Guide — replicate this to work here

This is the document to read before your first commit. It explains what we build with,
how work flows from a voice memo to shipped code, and the rules that keep a public,
agent-driven repo safe. It reflects how the project lead (Dinis Cruz) actually works —
the same method used in `SGraph-AI__App__Send` and `SGraph-AI__Tools` — and it is the
method other devs on this project are expected to replicate.

---

## 1. The Product Stack (what we build with)

**Front end — everything.** There is no backend. The product is static HTML + vanilla
JavaScript + Web Components. No SPA frameworks, no build step beyond what CI does.
Assets follow IFD-style immutable versioning (`v0/v0.1/v0.1.0/...`) as in the sibling
repos, so published versions never mutate.

**Hosting.** GitHub Pages (this repo → `website/`), with S3 + CloudFront where more is
needed. The domain is wired via AWS Route 53.

**Inference + billing.** OpenRouter. Per-user provisioning keys carry a credit limit;
OpenRouter meters and deducts. The margin is the key's credit limit — there is no
billing code. Guardrails on keys (model / provider / data-policy restriction) are how
the privacy tiers get enforced server-side.

**Audio.** WhatsApp voice notes are Opus-in-Ogg (the norm, 48kHz mono) or AAC-in-MPEG-4
(iPhone app-to-app forwards). Browsers decode both natively. Format is detected by
content, never by extension.

**Reuse before rebuild.** The building blocks already exist in `SGraph-AI__Tools`
(copies of the key docs are in `../tools/audio-transcribe/`):
audio-transcribe tool, sg-audio-decode, live-transcribe, the infographic generator,
and the LLM component library (`sg-llm-events.js`, `sg-llm-request.js`,
`sg-llm-infographic.js`, `sg-layout`).

**Python (only when unavoidable).** The single planned server-side piece is a
key-provisioning Lambda (deferred). When Python happens: `Type_Safe` from osbot-utils
(never Pydantic), `osbot-aws` (never raw boto3), pytest with **no mocks and no patches**.

**Encrypted vaults.** SG/Send vaults via the `sgit` CLI (`pip install sgit-ai`) are the
substrate for admin state, secret distribution and (later) the CRM. Zero-knowledge:
encryption is client-side; the server never sees plaintext.

## 2. The Repo Conventions (how the repo is organised)

- **Branches**: `dev` is the default branch — and, for now, production: it publishes
  the live domain. `dev` and `main` go to the same place until a separate production
  estate is split out (decision 6 Aug 2026).
  Feature branches: `claude/{description}-{session-id}` (agents) or `{yourname}/{slug}`
  (humans). PRs target `dev`.
- **Versioning**: CI owns it. On every push to `dev` (minor) or `main` (major) the
  pipeline bumps the root `version` file + `pyproject.toml`, updates the README badge,
  and pushes a tag. **Never edit these by hand.**
- **Doc naming**: `v{MAJOR}.{MINOR}.{PATCH}__{type}__{kebab-slug}.md` — version from the
  `version` file at time of writing, long keyword-dense slugs (the filename doubles as
  the abstract). Date-bucketed folders are `MM/DD/`.
- **Licence**: docs CC BY 4.0 with the standard footer; code Apache 2.0 (decided
  6 Aug 2026; the root `LICENSE` file is canonical).
- **The ciphertext rule**: an encrypted vault MAY be committed to this public repo;
  the vault key, any plaintext secret, and the OpenRouter management key MUST NOT.
  Nothing that decrypts what is committed may ever be committed.

## 3. The Working Method (how work actually flows)

This is the part that is genuinely different from most projects, and it is the part to
replicate faithfully.

```
   voice memo (Dinis)                       the source of intent
        |
        v
   BRIEF  team/humans/dinis_cruz/briefs/MM/DD/     human-only folder
        |                                          (agents read, never write*)
        v
   AGENT SESSION (Claude Code)             reads rulebook -> reality -> brief
        |                                  works the queue, commits in the open
        +--> code / docs / site
        +--> issues/ updated IN THE SAME COMMIT as the work
        +--> reality updated IN THE SAME COMMIT as the change
        +--> role output -> team/roles/{role}/reviews/MM/DD/
        |
        v
   DEBRIEF  team/humans/dinis_cruz/debriefs/MM/DD/     back to the human
        |
        v
   PR -> dev -> CI: tag -> publish            every merge ships
```

\* Agents write into `briefs/` only when explicitly asked to file a document on the
human's behalf.

**The session loop** (what a Claude session — or a human dev — does):

1. Read `.claude/CLAUDE.md` (the rulebook).
2. Read `team/roles/librarian/reality/index.md` — what exists today. **If it is not in
   the reality doc, it does not exist**; proposals are labelled `PROPOSED`.
3. Read the newest brief in `briefs/` and the newest debrief in `debriefs/`.
4. Check `issues/` for the queue; claim work by moving/annotating issue files.
5. Do the work. Close/update issues, update reality, and commit — one coherent commit
   per unit of work, so the diff reads: what arrived → what was planned → what was done.
6. End the session with a debrief (and a completion report for larger packs).

**Issues-FS-lite** (`issues/`): open/blocked/done folders, `NNN-kebab-slug.md` files
with frontmatter (`created`, `priority`, optionally `source`, `estimated_effort`,
`blocked_on`). Four operations: OPEN, BLOCK, UNBLOCK, CLOSE — all just file moves plus
an appended note. The README tables are updated manually in the same commit.

**Reality discipline**: the Librarian maintains `reality/index.md` (EXISTS vs PROPOSED
plus a decision log). Briefs are aspirations; reality is facts; the two are reconciled
in every commit. No MEMORY.md anywhere — the repo is the memory.

**The agentic team**: roles in `team/roles/` (conductor, architect, dev, designer,
devops, librarian, qa, appsec, dpo, ambassador active today). A session "wears" a role
when producing role output; role reviews land under `reviews/MM/DD/`. Human folders
under `team/humans/` are the human's own space.

## 4. CI/CD (what happens on push)

`.github/workflows/ci-pipeline.yml`, on push to `dev` or `main`:

1. **increment-tag** (`owasp-sbot/OSBot-GitHub-Actions git__increment-tag@dev`):
   bumps `version` + `pyproject.toml` + README badge, commits ("Update release badge
   and version file"), pushes tag. dev = minor, main = major. Requires `pyproject.toml`
   to exist (learned the hard way — issue 018).
2. **build-pages** (dev only): pulls the bump commit, copies `version` →
   `website/version.txt`, stamps `<span id="site-version">` in the footer, uploads
   the site artifact.
3. **deploy-pages**: publishes to GitHub Pages.

The bump commit is pushed with `GITHUB_TOKEN`, which does not re-trigger workflows —
publishing happens inside the same run, after a pull. Tests will gate the tag step
(`needs: [run-tests]`) as soon as tests exist. Deploy jobs must degrade gracefully
when secrets are absent.

## 6. Onboarding Checklist (first hour)

1. Clone this repo; read the root README, then this guide.
2. Read `library/brief-pack/` 00→06 (what/why/architecture/money/tasks/outcomes).
3. Read `.claude/CLAUDE.md` and `team/roles/librarian/reality/index.md`.
4. Read the newest brief (`team/humans/dinis_cruz/briefs/`, newest MM/DD) and debrief.
5. Skim `issues/README.md`; pick something `open` that matches your strengths.
6. Branch from `dev`, do the work with issue+reality updates in the same commit,
   PR back to `dev`.
7. Never touch `version`/`pyproject.toml` versions; never commit anything that
   decrypts anything.

## 7. The Principles Behind The Method

- **Open by default.** Everything is published as it is produced (CC BY 4.0 docs).
  Openness shrinks the legal surface and is the strategy, not a side effect.
- **One motion.** The product does one job in one pass; the working method mirrors it —
  small complete units, shipped whole.
- **The mechanism must be visible and stoppable.** Spend-capped keys, guardrails,
  auto-tags, reality docs: every mechanism leaves a visible trail and has an off switch.
- **Honest maturity labels.** Explorer-stage work is labelled as such; nothing is
  claimed that does not exist.
