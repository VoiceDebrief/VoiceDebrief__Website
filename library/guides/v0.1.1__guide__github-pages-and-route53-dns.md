# Guide: GitHub Pages Hosting And Route 53 DNS — How It Works And How To Repeat It

**version** v0.1.1
**date** 29 July 2026
**from** Claude (session agent), verified against this project's live setup
**to** Anyone wiring a domain to a GitHub Pages site on another SGraph project
**type** Guide

The no-backend architecture makes hosting = GitHub Pages + DNS. This guide explains
exactly how this project's hosting works end to end, what each piece does, and gives
the repeatable checklist for the next project.

---

## 1. How Our GitHub Pages Setup Works

**Publishing is a CI job, not a branch.** We use the "GitHub Actions" Pages source
(not the legacy deploy-from-branch). In [`ci-pipeline.yml`](../../.github/workflows/ci-pipeline.yml),
on every push to `dev`:

```
  increment-tag            bumps `version` + pyproject + README badge, pushes tag
      -> build-pages       pulls the bump commit, stamps the version into
                           website/index.html + website/version.txt,
                           actions/configure-pages (enablement: true),
                           actions/upload-pages-artifact  (path: website/)
      -> deploy-pages      actions/deploy-pages@v4 into the github-pages
                           environment -> the artifact becomes the live site
```

Key properties:
- What you see at the URL is **exactly the uploaded artifact** — no Jekyll, no build
  magic (`website/.nojekyll` keeps it that way).
- The site is version-stamped at publish time; `version.txt` tells you what's live.
- `permissions: pages: write, id-token: write` on the deploy job is what authorises
  the deployment (OIDC), and the `github-pages` environment records the history.

**Where it serves from.** Without a custom domain, an org project site serves at
`https://<org>.github.io/<Repo-Name>/`. With a custom domain configured, GitHub's CDN
serves the same artifact for that hostname at the root path instead.

## 2. How The DNS Side Works (What The Route 53 Record Does)

The record created for this project (verified resolving, 29 Jul 2026):

```
   whatsapp-voice-transcription.sgraph.ai.   300   IN   CNAME   sgraph-ai.github.io.
```

What actually happens when a browser visits the domain:

```
   browser
     | 1. DNS query: whatsapp-voice-transcription.sgraph.ai?
     v
   Route 53 (authoritative for sgraph.ai)
     | 2. answer: CNAME -> sgraph-ai.github.io
     |    (resolver then follows it to GitHub Pages' A/AAAA records --
     |     four anycast IPs of GitHub's Fastly-backed CDN)
     v
   GitHub Pages CDN edge
     | 3. HTTP request arrives with  Host: whatsapp-voice-transcription.sgraph.ai
     | 4. GitHub looks up which repo has CLAIMED that hostname
     |    (Settings -> Pages -> Custom domain) and serves that repo's
     |    deployed artifact
     v
   our website/ artifact, at the domain root
```

Two things follow from step 4 that people often miss:

- **The CNAME points at the ORG domain, not the repo.** `sgraph-ai.github.io` is the
  same value for every project in the org. The *repo* is selected purely by the
  hostname claim in that repo's Pages settings — DNS never mentions the repo.
- **Unclaimed hostname = takeover risk.** If DNS points at `<org>.github.io` but no
  repo claims the hostname, ANY GitHub user could claim it. Hence verification (§4).

**Why CNAME and not Alias here.** A CNAME is only legal on a *subdomain* (it was
correct to set Alias: No). For an **apex** domain (`sgraph.ai` itself) CNAME is not
allowed — there you use either a Route 53 **ALIAS/A record** to GitHub Pages' four
IPs (`185.199.108.153`, `.109.153`, `.110.153`, `.111.153` + their AAAA twins) or,
better, don't put product sites on the apex at all. Subdomain-per-product is the
cleaner pattern and what we do. TTL 300 is a good default (fast to fix mistakes).

## 3. The GitHub Side (What Must Be Set In The Repo)

Settings → Pages, in this order:

1. **Source: GitHub Actions** (done at project setup — our workflow deploys).
2. **Custom domain**: `whatsapp-voice-transcription.sgraph.ai` → Save. GitHub then:
   - starts serving the artifact for that Host header (HTTP works immediately once
     DNS resolves), and redirects the old `<org>.github.io/<repo>/` URL to the domain;
   - kicks off **Let's Encrypt certificate provisioning** for the hostname.
3. **Enforce HTTPS**: tick it **once the certificate exists** (the checkbox stays
   disabled until then). This turns HTTP into a 301 to HTTPS.

Certificate provisioning is usually minutes but can take up to ~24h. It requires the
DNS record to be resolving (ours is). If it's stuck: remove and re-add the custom
domain to retrigger, and check the domain has no **CAA records** that exclude
`letsencrypt.org` (a CAA on `sgraph.ai` would block issuance for every subdomain).

Note for Actions-source Pages: the Settings entry is the authority for the domain.
(The classic `CNAME` file in the site root is how *branch*-source Pages remembers the
domain — harmless to include, but not what drives our setup.)

## 4. Domain Verification (Do This Once Per Org — Takeover Protection)

Org Settings → Pages → **Add a verified domain** → `sgraph.ai`. GitHub gives a TXT
record like:

```
   _github-pages-challenge-sgraph-ai.sgraph.ai.   TXT   "<token>"
```

Add it in Route 53. Once verified, **only repos in this org can claim
`*.sgraph.ai` hostnames** on GitHub Pages — closing the takeover window for any
sgraph.ai subdomain that points at GitHub before/after a repo claims it. One TXT
covers the whole domain and all future projects.

## 6. The Repeatable Checklist For The Next Project

1. Repo: Pages workflow (copy [`ci-pipeline.yml`](../../.github/workflows/ci-pipeline.yml)'s
   `build-pages`/`deploy-pages` jobs; artifact = the site folder; `.nojekyll`).
2. First deploy to the default branch → site live at `<org>.github.io/<Repo>/`.
3. Route 53: `CNAME  <product>.sgraph.ai  ->  <org>.github.io`  (TTL 300, Alias: No).
4. Repo Settings → Pages → Custom domain = `<product>.sgraph.ai` → Save.
5. Wait for the certificate (minutes–24h) → tick **Enforce HTTPS**.
6. Org verified domain TXT record — once per org, if not already done.
7. Smoke: `curl -I https://<product>.sgraph.ai` → 200 with `server: GitHub.com`;
   old github.io URL redirects; `version.txt` matches the latest tag.
8. Update the project's reality doc with the domain, in the same commit as any
   site config change.

## 7. Troubleshooting Quick Table

| Symptom | Likely cause |
|---------|-------------|
| DNS resolves, GitHub returns 404 for the hostname | Custom domain not (or no longer) set in the repo's Pages settings |
| "Domain is already taken" when claiming | Another repo (possibly outside the org) claimed it — org verification (§4) prevents/fixes this |
| HTTPS cert never appears | DNS not propagated when set (re-add the domain), or CAA on the domain blocks Let's Encrypt |
| Site serves but assets 404 | Absolute paths assuming the `/<Repo>/` project path (or vice versa) — use relative paths so both origins work |
| Old github.io URL shows content instead of redirecting | Redirect appears only after the custom domain is saved and healthy |
| Wrong site for the hostname | The hostname is claimed by a different repo in the org |
