# Content architecture: how agents publish without breaking things

*Part of the [project library](https://whatsapp-voice-transcription.sgraph.ai/library/) — every doc behind this product, organised by audience.*

**status** EXISTS — shipped as issue 039, 6 Aug 2026.
**why now** A Claude Routine now runs the Journalist at 5am daily. Its first unattended
run was good work, but look at what it had to *do*: splice an `<article>` block into a
145-line presentation file at exactly the right indentation, and simultaneously perform
surgery on an existing article's markup to drop a stale caveat. That is the wrong job to
hand a machine at 5am with nobody watching — and the wrong job to hand a person.

---

## 1. What was wrong with editing the HTML

| Problem | Why it bites |
|---|---|
| **Content lived in markup** | Publishing meant writing HTML, so a missing `</article>` shipped a broken page. Nothing validated it. |
| **Every publish touched one shared file** | Two agents publishing the same day conflict in `index.html` — and conflicts in generated-looking markup are the nastiest kind to resolve. |
| **Links were hand-written** | `blob/qa/issues/open/034-…` went stale the moment the issue moved to `done/`, and `qa` is a branch that keeps moving. The routine had to spot and fix that by eye. |
| **Ordering was manual** | The agent had to decide *where* in the file a post goes. There is no reason a machine should make that call. |
| **Nothing was queryable** | No way to ask "what shipped in v0.1.18?" or to show the latest post on another page — the data only existed as markup. |
| **Correcting a post meant re-doing surgery** | Removing a caveat from an existing post is a diff against markup, not against meaning. |

## 2. The shape now

```
content/                                   ← the source of truth (committed)
├── updates/2026/08/06/v0.1.20__update__chat-edits-materials.md
├── versions/v0.1.20.md
└── videos/chat-with-your-voice-memos.md
                    │
                    ▼   scripts/build_content.py   (stdlib only, no deps)
website/                                   ← build output (gitignored, never edited)
├── updates/index.html · updates.json · feed.xml
├── videos/index.html  · videos.json
└── versions/versions.json
```

**The rule that makes it work: publishing is adding one file, and nothing else.**

## 3. The five properties that make an agent's change atomic

1. **One post, one file, no index.** Ordering is derived from `date` + `version`, so no
   agent ever decides placement, and two agents writing different days cannot collide.
   The "central JSON" exists — `updates.json` — but it is *generated*, never
   hand-maintained. A hand-maintained index is precisely the shared file we set out to
   remove.
2. **Facts in, links out.** The author writes `version: v0.1.20` and `issues: 035`. The
   build derives the diff against the *previous released tag* and finds each issue file
   *wherever it currently lives*. The whole class of stale-link bugs is gone, because
   nobody writes a URL.
3. **The build validates, and refuses.** Missing date, malformed version, a folder that
   disagrees with its frontmatter, a duplicate slug, an issue number that does not
   exist, an unclosed code fence, a published video with no YouTube id — each fails
   `--check`, which runs in the CI test gate *before* the tag and the deploy. A bad post
   cannot reach the site; the 5am agent gets a red build, not a broken page.
4. **Presentation is not the agent's business.** Layout lives in
   `scripts/templates/*.html`. A designer can restyle every post without touching
   content; an agent can publish without seeing a single tag.
5. **Drafts are first-class.** `status: draft` means "written, held back" — an agent can
   prepare a post (or a video whose id it does not have yet) without publishing it.

## 4. What this buys beyond tidiness

- **`updates.json` / `videos.json`** — any page can now show "the latest update" or the
  newest demo, and any future daily action can *read* the published record rather than
  scrape a page.
- **`feed.xml`** — RSS, free, from the same source.
- **Permalinks** — every post has a stable `#slug`, so an update can be linked directly.
- **Correcting a post is editing that post's own file** — the caveat removal that made
  the routine perform HTML surgery is now a one-line edit to one markdown file.

## 5. Adding a new content type

A new type is a `load_*()` function, a template, and two lines in `build()`. Videos were
added this way in the same commit as the architecture — the second type took under an
hour, which is the evidence that the layout generalises. Candidates: case studies,
release notes for the API, a changelog page fed from `content/versions/`.

## 6. What the Journalist routine should do now

The daily prompt should end with something like:

> Publish by adding **one markdown file** under `content/updates/YYYY/MM/DD/` following
> `content/README.md`. Never edit `website/` — it is generated. Never write a GitHub
> URL: use `version:` and `issues:` and let the build derive them. Run
> `python3 scripts/build_content.py --check` before committing, and push to `qa`.
