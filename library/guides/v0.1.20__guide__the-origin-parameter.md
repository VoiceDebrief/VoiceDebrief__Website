# What `?origin=` does

*Part of the [project library](https://whatsapp-voice-transcription.sgraph.ai/library/) — every doc behind this product, organised by audience.*

**status** The parameter is **GONE** as of 6 Aug 2026 (issue 041). It existed from M1
until then. This guide is kept because the *question* — where does the engine come
from? — is still a live one, and because how the parameter was removed is the more
useful lesson.
**audience** anyone working on the app, and anyone reviewing its security.

---

## 1. The one-sentence answer

`?origin=` tells the app **which server to load the transcription engine from** —
because this product does not contain an engine, it borrows one at runtime.

## 2. Why the app needs an origin at all

The whole product is a browser page with no backend. It does not ship the audio
pipeline: it *imports* the proven `audio-transcribe` engine from the SGraph tools site
over the network, live, as ES modules ([the spike verdict, dev pack brief
06](../dev_packs/v0.1.1__audio-transcribe-integration/03__dev__implementation-brief.md)):

```js
// website/app/engine.js
import(`${ORIGIN}/en-gb/audio-transcribe/api/api-transcribe.js`)
import(`${ORIGIN}/core/sg-tool-api/v0/v0.1/v0.1.0/sg-tool-api.js`)
// …ten modules in total
```

`ORIGIN` comes from `website/app/config.js`. Its default is
`https://dev.tools.sgraph.ai`. That default is why the app works with no query string
at all — and why the QA live check verifies that host is up and sends
`access-control-allow-origin: *`. If the tools site is unreachable, our app cannot boot,
which is a deliberate trade (reuse over rewrite) and the reason boot failure has its own
error message.

## 3. What the parameter was for

Two jobs, both development:

1. **Running the app against a local copy of the engine.** In a sandbox with no network
   route to the tools site, the tests serve a mirror locally. This turned out **not to
   need the parameter at all**: the test rig intercepts requests to the real origin and
   answers them from the mirror, which is why removing it broke nothing.
2. **Trying a different engine build** — for example pointing at production
   `tools.sgraph.ai` instead of `dev.` — without editing, rebuilding or deploying
   anything.

It is not a user-facing feature. Nothing in the UI sets it, and nothing links to it.

## 4. Why it was removed (6 Aug 2026)

Read what the parameter actually controls: **the URL that JavaScript is imported and
executed from, inside our page.** That code runs with everything the page has —
including the user's OpenRouter API key, which lives in
`localStorage['sg-openrouter-mgmt-key']`.

Before the allow-list, this link was enough:

```
https://whatsapp-voice-transcription.sgraph.ai/app/?origin=https://somewhere-else
```

The domain is ours and looks entirely trustworthy; the page loads normally; and every
engine module comes from someone else's server. That code could read the key out of
localStorage and post it anywhere. There is no CSP on the site to catch it, and the
attacker's own server can send whatever CORS headers it likes, so nothing else stood in
the way. In short: a credential-theft vector wearing a legitimate URL.

**The first fix was an allow-list** — restrict the value to the two tools origins plus
localhost. It works, and it was written twice independently (here and, as issue 037, on
the review-pack branch), which is fair evidence the finding was real.

**The fix that shipped is removal.** Dinis's call, and the better one: *"the solution is
not to have that feature at all, since we can hardcode that origin."* The parameter
existed only for development, and development never actually needed it — see §3. So:

```js
// website/app/config.js — the whole of it now
export const ORIGIN = 'https://dev.tools.sgraph.ai'
```

An allow-list is a control that has to stay correct forever: someone widens it for a
plausible reason, or a URL-parsing edge case slips through, and the hole is back. A
capability that no longer exists cannot be got wrong. The tests assert the stronger
property — that `config.js` contains no `location.search`, `URLSearchParams` or
`searchParams` at all — because that is what actually cannot regress.

A **Content-Security-Policy** on the app page (from the review-pack branch) pins
`script-src` to self plus the two tools origins, which is defence in depth for the whole
class rather than this one parameter.

## 5. Pointing at a different engine today

- **In a checkout**: change the one line in `website/app/config.js`. It is a constant,
  which is the honest place for a build-time decision.
- **In a test**: intercept requests to the origin and answer them locally — what
  `MIRROR_DIR` mode does in `tests/integration/*.test.mjs`.
- **In a deployed page**: you cannot, and that is the point.

To confirm which engine a page is running, open the ⚙ debug pane — every LLM call shows
its model and full request — or check the browser's network tab for where the modules
were fetched from.

## 6. If you are tempted to make it configurable again

Read §4 first. Anything that lets an input choose an `import()` target is choosing which
code runs beside the user's API key. If a genuine need appears, prefer a build-time
constant per estate over anything read at runtime — and never anything read from the
URL.
